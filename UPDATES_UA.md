# Оновлення поточного FRE LAUNCH (Vue/Tauri)

Канал: `update-channel.json`, публічні Releases репозиторію
[Freeze0102/FRE-LAUNCH](https://github.com/Freeze0102/FRE-LAUNCH/releases).
Версія нового коду — **0.5.8**. Це не оголошення готового Windows-релізу.
Стара React-реалізація у корені має іншу систему збірки; ці зміни її не оновлюють.

## Поведінка

Після ініціалізації лаунчер перевіряє `releases/latest/download/latest.json`.
За звичайного з'єднання новий інсталятор завантажується автоматично.
У верхній панелі видно прогрес, а після перевірки підпису — кнопку
«Перезапустити й оновити» та повідомлення у наявному оформленні Modrinth.
Можна продовжити користування: штатний Tauri/NSIS механізм встановить
підготовлене оновлення під час закриття лаунчера, без примусового повторного
запуску. Натискання кнопки закриває, оновлює та повторно відкриває лаунчер.
Нові вікна авторизації або інший дизайн не додаються.

На з'єднанні з лімітом трафіку завантаження запускається кнопкою.
Невдала перевірка мережі вважається лімітованим з'єднанням. Після мережевої
помилки перевірка повторюється через 15 хвилин; після помилки завантаження
кнопка дозволяє повторити спробу. Незавершене завантаження не встановлюється.
Готові байти зберігаються в пам'яті процесу; після аварійного завершення їх
потрібно завантажити знову. Debug/dev-збірки не перевіряють оновлень.

Дозволено лише HTTPS-адресу конкретного версійованого Windows-інсталятора
цього репозиторію. Максимум — 256 MiB; задано таймаути з'єднання/завантаження.
Перед передачею NSIS перевіряються розмір, Windows-заголовок і Minisign-підпис
вбудованим публічним ключем FRE LAUNCH. Непідписаний, пошкоджений або підписаний
іншим ключем файл не потрапляє в чергу встановлення. Вікно має лише updater
permission `allow-check`; прямі plugin download/install дозволи не видаються.
Стару адресу, ключ Modrinth і налаштування їхнього Digicert прибрано також із
`tauri-release.conf.json`.

## Ключ і локальна збірка

Публічний ключ зафіксовано у `update-channel.json`. Приватний створено локально
в `.fre-update-keys/frelaunch.key`; каталог виключений із Git.
Його не можна завантажувати в репозиторій або додавати до Releases.
Власник має зберегти резервну копію цього ключа у захищеному місці: заміна
публічного ключа в наступному випуску зламає перевірку у вже встановлених клієнтів.
Локальний ключ зараз без пароля; можна змінити захист ключа, зберігши ту саму пару.

Запуск локальної перевіреної збірки:

```powershell
.\FRE-MODRINTH-LOCAL.ps1 -BuildWindows
```

Сценарій використовує локальний ключ, якщо не задано
`TAURI_SIGNING_PRIVATE_KEY`. Для іншого середовища ця змінна має містити шлях
до того самого ключа або підтримуваний Tauri вміст; пароль за потреби задається
через `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`. Ключ використовується тільки під
час підписання збірки та не вбудовується у програму. Після завершення сценарій
відновлює попереднє значення змінної.

Якщо Windows Python alias не запускається, передай справжній шлях:
`-PythonExe 'C:\шлях\python.exe'` або задай `FRE_LAUNCH_PYTHON`.
Tauri викликається з `--ci`, щоб підписувач не очікував інтерактивного введення
пароля. Це локальний неінтерактивний режим CLI; GitHub Actions не запускаються.
Неправильний/відсутній пароль захищеного ключа зупинить збірку.

Desktop-залежності встановлюються з frozen lockfile. Зафіксовані security
оновлення, точкові винятки перевірки віку та два відкриті dev-findings описано
у [SECURITY_DEPENDENCIES.md](scripts/modrinth-fork/SECURITY_DEPENDENCIES.md).

Звичайний build зупиняється, якщо справжня перевірка TypeScript або Tauri
завершується помилкою. Вимикати цей gate для випуску не потрібно.
Результат успішного build — NSIS `.exe` та `.exe.sig` у
`FRE-Modrinth-Source/target/release/bundle/nsis`.

## Випуск через Releases без Actions

1. Виправити блокери повного build і виконати перевірку нової збірки та
   реального NSIS-переходу в ізольованій Windows VM. Встановлену користувацьку
   EXE, профілі та світи для тестування не використовувати.
   Чинний [SECURITY_NOTICE.md](SECURITY_NOTICE.md) залишається в силі.
2. Для кожного наступного випуску підвищувати `version` у `update-channel.json`,
   не змінюючи пару ключів. Згенерувати й підписати нову збірку локально.
3. Підготувати файл нотаток релізу. Додати посилання на коміт відповідного
   вихідного коду; повний pin Modrinth і GPL notices залишаються у репозиторії.
4. Створити пакет, передавши шлях до підписаного інсталятора та нотаток:

   ```powershell
   node scripts/modrinth-fork/package-update.mjs "ШЛЯХ_ДО_ІНСТАЛЯТОРА.exe" "NOTES.md"
   ```

   Помічник **криптографічно перевіряє** файл та підпис ключем каналу до
   запису результату. У новому каталозі `release-staging/vVERSION` створює
   `FRE-LAUNCH-Windows-x64-Setup.exe`, `.exe.sig`, `latest.json`,
   `SHA256SUMS.txt` і `NOTES.md`. Наявний каталог не перезаписує.
5. Створити draft GitHub Release із тегом `vVERSION` на перевіреному коміті.
   Завантажити чотири файли пакета (EXE, SIG, JSON, SHA256), додати нотатки.
   Публікувати як Latest лише після завантаження всіх файлів і перевірки
   анонімного доступу. Не замінювати EXE вже опублікованої версії.

Сам помічник нічого не завантажує в GitHub, не запускає Actions і не встановлює
інсталятор. Формат статичного JSON та підписів відповідає
[офіційному Tauri updater](https://v2.tauri.app/plugin/updater/).
Перевірка пакета використовує стандартний
[формат Minisign](https://jedisct1.github.io/minisign/) та Ed25519/Blake2b
із [Node crypto](https://nodejs.org/api/crypto.html).
Цей підпис підтверджує походження оновлення; він не є Windows Authenticode
сертифікатом і не замінює перевірку безпеки самого інсталятора.

### Локальний draft та перевірка доставки

Для підготовленого пакета з нотатками й `PROVENANCE.json` є окремий явний
сценарій. Він працює лише з `Freeze0102/FRE-LAUNCH`, перевіряє реальний підпис,
хеш, версію, URL, дані scan і доступність точного source commit. Наявний asset
з іншими байтами та вже опублікований release не перезаписує.

```powershell
node scripts/modrinth-fork/publish-update.mjs --dry-run
node scripts/modrinth-fork/publish-update.mjs
```

Другий виклик створює **draft** і завантажує тільки EXE, SIG, JSON, SHA256
та публічний PROVENANCE. Digest кожного файлу звіряється з GitHub.
Використовується наявна авторизація Git через credential helper; токен не
виводиться і не зберігається у файлі. Приватний signing key не завантажується.
Після рішення про випуск явний `--publish` переводить перевірений draft у Latest.
Жоден із цих викликів не запускає GitHub Actions.

Після публікації перевірка з боку користувача, без GitHub-токена:

```powershell
node scripts/modrinth-fork/smoke-update.mjs 0.5.8
```

Вона анонімно отримує справжній Latest manifest, завантажує Windows-файл,
перевіряє підпис і збіг зі scan-хешем, а також що версія новіша за 0.5.8.
Інсталятор не виконується. Реальний перезапуск установленого клієнта —
окремий етап; сам успіх цього smoke не доводить NSIS-перехід.

## Перше встановлення та межі перевірок

У старій встановленій EXE updater був вимкнений. Їй потрібне **одне ручне
встановлення** нової перевіреної збірки; лише після цього вона зможе отримувати
наступні випуски автоматично. Самої публічності репозиторію недостатньо:
у Latest Release мають бути доступні валідний `latest.json` і підписана EXE.

Локально перевіряються Python-патчі на чистому pin, стан frontend-updater,
справжні Tauri-підписи та нативний Rust-код. Це не доводить працездатність
реального NSIS-оновлення, Microsoft-входу або ігрового рушія.
Поточні результати й блокери наведено у [звіті аудиту](AUDIT_UA.md).

На 01.11.2026 локальний Windows build **0.5.8 успішний**: NSIS та його
справжній підпис створені, підпис перевірений; Defender не виявив загроз
у нових EXE й інсталяторі. Локальний пакет `release-staging/v0.5.8` має статус
**SECURITY-REVIEW-ONLY**. Він не опублікований і не є завершеним тестом
встановлення/оновлення у Windows VM. Старий інцидент безпеки залишається відкритим.
